# Kotobaseed pre-launch audit (2026-06-07)

**Author:** Claude, after the 2026-06-06 patch session and Sophia's frustration call.
**Scope:** Six areas Sophia called out — auth surface, booking lifecycle, migration tree, frontend duplication, endpoint shape, Playwright readiness.
**Status:** Findings only. No code changes in this commit.

The intent is to surface every known fragility *before* I write more code, so we ship in safe slices instead of patching reactively. Companion to the earlier `AUDIT.md` (file-by-file verdicts), which I have not edited.

## Executive summary

Feature-complete on paper, but several mainline flows have correctness gaps and the codebase has accumulated enough duplication that a schema change ripples through 3–5 files. Top of the risk list:

| # | Risk | Severity | Mainline flow affected |
|---|---|---|---|
| 1 | Tutor can mark a booking complete *before* the lesson has happened. There is no timing gate at all. | **Critical** | Booking quality + minutes-used accounting |
| 2 | "No-show" status does not exist. Tutors have no way to mark a student a no-show. | **Critical** | Trust + future fraud detection |
| 3 | Recurring weekly plans generate child bookings without honouring `min_booking_lead_minutes` or the cancellation cutoff. | **High** | Recurring bookings |
| 4 | WebSocket auth requires `?token=` query param and has no cookie fallback. Cross-subdomain SSO users who never logged in directly on the subdomain lose realtime inbox + notifications. | **High** | Inbox, in-app notifications |
| 5 | Two pages still gate UI on `localStorage` `token` instead of `currentUser` (`StaffSupport.jsx`, `ModulesStorefront.jsx`). Cookie-only sessions get bounced to /login. | **High** | Staff support + modules storefront |
| 6 | `Booking` JSON shape is inconsistent across views (`tutor_display_name` vs `student_name`; `cancellation_cutoff_hours` present in one view, missing in others). | **High** | Bookings UI |
| 7 | The avatar URL field is called four different names (`avatar_url`, `photo_url`, `teacher_avatar_url`, `tutor_photo_url`) and the `ui-avatars.com` fallback is duplicated 5× inline. | **Medium** | Every page that shows a face |
| 8 | Cancel/complete/reschedule endpoints are not idempotent. Double-click → 409. | **Medium** | Booking management |
| 9 | Policy fields (`cancellation_cutoff_hours`, `min_booking_lead_minutes`, `free_trial_minutes`) are fetched from 2–3 different endpoints by different components. | **Medium** | All settings panels |

| 11 | Playwright is not installed; no browser-driven tests exist anywhere. | **Critical for process** | Every flow Sophia tests |

## 1. Auth surface

### What's correct now
- `Navbar`, `ProtectedRoute`, `TeacherRoute`, `AdminRoute`, `InboxDropdown`, `Inbox`, `InboxContext`, `Support`, `ArchivedConversations`, `ProjectDetail`, `ProjectList`, `App.ApexShell` all gate on `useAuth().currentUser` (cookie-aware). ✓
- `AuthContext` boot probes `/users/me` unconditionally and respects the focus event for cross-tab logout propagation. ✓
- `/auth/logout` clears the cookie, bumps `User.token_invalidation_at`, and accepts unauthenticated callers for clean stale-token logout. ✓
- Cookie: `Domain=.kotobaseed.net; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000s` (30 d), end-to-end verified with curl. ✓
- Backend `get_current_user` reads `Authorization: Bearer` *or* `koto_token` cookie via `token_from_request` (`backend/security.py:108`). ✓

### What's still wrong

**A. Two more pages gate on `token` instead of `currentUser`.**
- `frontend/src/pages/staff/StaffSupport.jsx:390-405` — `const { token } = useAuth()` then `if (!token) navigate('/login')`.
- `frontend/src/pages/ModulesStorefront.jsx:51-55` — same pattern; gates the subscribe button.

Both are quick fixes (`currentUser` swap), same shape as yesterday's sweep.

**B. WebSocket endpoints have no cookie fallback.**
- `backend/routers/conversations.py:1135` — `@router.websocket("/{conversation_id}/ws")` uses `get_user_from_token()` which only decodes a JWT query param.
- `backend/routers/conversations.py:1207` — `@router.websocket("/ws")` same pattern.

If a user is signed in via the shared cookie alone (e.g. landed on a tutor subdomain via cookie without a fresh login form submit), they have no localStorage JWT to pass to the WS URL. `InboxContext.jsx:41` falls back to localStorage and silently disables realtime when empty. **Result:** the inbox bell never updates until the user manually refreshes.

**Proposed fix:** WS handshake reads the cookie from the upgrade request. Starlette exposes `websocket.cookies` — we'd swap `get_user_from_token(token)` for a path that prefers the cookie and falls back to the query param. (Token-in-URL is also unfortunate from a logging perspective — URLs end up in nginx/Caddy access logs.)

**C. `get_current_user_optional` skips the `token_invalidation_at` check.**
- `backend/deps.py:93-109` decodes the JWT but does not compare `iat` against the user's `token_invalidation_at`.

After logout-everywhere, an optional-auth endpoint that received the old Authorization header would still see a valid user object until the JWT itself expires. The cookie clear mitigates this for browsers; headers passed by tools or anything that cached the token slip through. Low practical risk but inconsistent.

**D. Cookie is not refreshed on activity.**
- No endpoint calls `set_auth_cookie` on a successful authenticated request. With a 30-day cookie this is far less urgent than the original 30-min default, but it means a user who stays signed in for 30 days suddenly gets a silent 401 instead of a smooth re-login.

**Proposed fix (low priority):** stamp a fresh `Set-Cookie` on `/users/me` whenever it succeeds. Cheap, transparent.

**E. `OnboardingReturn.jsx:62` passes `token=${token}` in a URL fragment when handing off to the tutor dashboard subdomain.**

The cookie now does this work; the fragment is a fallback. Worth keeping for cookie-blocking browsers but should not be the only signal. Already true; flagging for awareness.

### Playwright tests that would catch these
- "Inbox bell updates without page refresh after the other party messages me, from a cross-subdomain logged-in session."
- "Staff support page loads when the user is signed in only via cookie."

## 2. Booking lifecycle

### The state machine today

`BookingStatus` enum (`backend/models.py:636`): `PENDING_PAYMENT`, `PENDING_GROUP_MIN`, `CONFIRMED`, `COMPLETED`, `CANCELLED`, `REFUNDED`. No `NO_SHOW`.

| Transition | Endpoint | File:Line | Server-time gated? |
|---|---|---|---|
| _ → PENDING_PAYMENT (1:1) | POST `/lesson-packs/{id}/start-checkout` | `tutor_site.py:1351` | ✓ future-time, ✗ lead-time only at slot-list |
| _ → PENDING_PAYMENT (group) | POST `/group-sessions/checkout` | `group_sessions.py:282` | ✓ |
| _ → CONFIRMED (trial) | POST `/trial-booking` | `tutor_site.py:1117` | ✓ |
| PENDING_PAYMENT → CONFIRMED | Stripe webhook | `pledges.py:184` | ✓ idempotent |
| PENDING_PAYMENT → PENDING_GROUP_MIN | Stripe webhook (group) | `pledges.py:238` | ✓ idempotent |
| PENDING_GROUP_MIN → CONFIRMED | Cron (hourly) | `group_lessons.py:107` | ✓ |
| PENDING_GROUP_MIN → REFUNDED | Cron (no-min) | `group_lessons.py:107` | ✓ |
| PENDING_PAYMENT (recurring) → CANCELLED | Cron | `recurring_bookings.py:212` | ✓ |
| CONFIRMED → REFUNDED | POST `/users/me/bookings/{id}/cancel` | `users.py:478` | ✓ cancellation cutoff |
| CONFIRMED → CONFIRMED (reschedule) | POST `/users/me/bookings/{id}/reschedule` | `users.py:592` | ✓ |
| CONFIRMED → COMPLETED | POST `/bookings/{id}/complete` | `tutor_site.py:2251` | **✗ NO TIMING GATE** |
| CONFIRMED → NO_SHOW | _does not exist_ | — | n/a |

### Critical gaps

**A. Mark complete has no timing gate.**
`tutor_site.py:2251` only checks `booking.status == CONFIRMED`. There is no check that `now >= scheduled_at + duration_minutes`. A tutor could mark a future booking complete by accident and the minutes-used counter would tick up immediately. This is exactly what you flagged.

**Proposed contract:**
- Reject with 400 + clear message if `now < booking.scheduled_at + timedelta(minutes=booking.duration_minutes)`.
- Allow a 5-minute slop window before the lesson actually ends so the tutor can mark-complete the moment they hang up (avoids "the button doesn't work yet"). i.e. permit when `now >= booking.scheduled_at + duration_minutes - 5min`.

**B. No NO_SHOW status or endpoint.**

**Proposed contract:**
- Add `BookingStatus.NO_SHOW = "no_show"`.
- New endpoint `POST /bookings/{id}/no-show` — tutor-only, requires `now >= scheduled_at + 15min` (grace period), optional `reason` text field.
- The flip does NOT refund the student. The booking still counts against trial-one-per-pair.
- Side effects: notification to student ("you missed your lesson with X — message them to rebook"), tutor's analytics get a `no_show_count` tick.
- Tests cover: cannot fire before 15min grace; idempotent if already NO_SHOW; not allowed from any state other than CONFIRMED.

**C. Recurring plans bypass `min_booking_lead_minutes` and `cancellation_cutoff_hours` at generation time.**
`recurring_bookings.py:79-190` (`generate_bookings_for_plan`) ensures `lookahead_weeks` future child bookings exist but does not check the tutor's lead time at all. A plan with anchor "tomorrow 9am" and tutor `min_booking_lead_minutes=1440` will still generate tomorrow's child.

**Proposed fix:** the generator should skip a candidate slot if `slot < now + max(lead, cancellation_cutoff)`. The first scheduled child of a freshly created plan should already be paid for at plan-creation time (the create endpoint runs a Stripe Checkout), but this gap can show up after a plan is paused/resumed.

**D. Cancel, complete, reschedule are not idempotent.**
A double-click on "Cancel" returns 409 because the second call sees the new status. Annoying but not dangerous.

**Proposed fix:** each transition endpoint short-circuits with a 200 + the current state if the booking is already in the target state. Same shape as `pledges.py:202` which does this correctly for webhooks.

**E. No tutor-side cancel endpoint for 1:1 bookings.**
Only group sessions can be cancelled by the tutor (`group_sessions.py`, `DELETE /group-sessions/{id}`). A tutor who needs to cancel a 1:1 has no API path; the workaround is admin intervention. Possibly intentional (forces a conversation through the inbox first) but worth deciding consciously.

### Playwright tests that would catch these
- "Mark complete is disabled while the lesson is in the future, becomes enabled 5 minutes before scheduled end."
- "No-show button only appears after 15 minutes past start time."
- "Double-click on Cancel does not show an error toast."
- "Pausing and resuming a recurring plan does not regenerate a child within the lead-time window."

## 3. Frontend duplication + endpoint shape

### Symptoms

**A. Booking JSON shape varies by view.**
The same `Booking` is rendered by:
- `MyBookings.jsx` (student view) — expects `tutor_display_name`, `tutor_slug`, `cancellation_cutoff_hours`, `pack_name`.
- `BookingsManager.jsx` (tutor view) — expects `student_name`, `lesson_pack_id`.
- `NextLessonBanner.jsx` — expects `tutor_display_name`, `tutor_slug`.
- `OverviewPanel.jsx` → `NextLessonCard.jsx` — expects `student_name`.

The two endpoints serialise differently (`/users/me/bookings` vs `/tutor/bookings`) and each view has hard-coded knowledge of the shape. Renaming a single field requires editing multiple components.

**Proposed fix:**
- Create `StudentBookingRead` and `TutorBookingRead` Pydantic models with **shared base fields** + a discriminator. Each endpoint returns the appropriate type.
- Create one `<BookingCard>` React component that accepts both shapes (or a normalised local shape) and renders consistently. Replace ad-hoc renders.

**B. Avatar field has four names + duplicated fallback.**
- `User.avatar_url`
- `Tutor` projects `user.avatar_url` as `photo_url`
- `Project` exposes `teacher_avatar_url`
- `DiscoverItem` exposes `tutor_photo_url`

Plus the `ui-avatars.com` fallback is inlined in `Navbar.jsx:254`, `Profile.jsx:165, 272, 317`, `ProjectDetail.jsx:411`, ten other places.

**Proposed fix:**
- One backend convention: every entity exposes its photo as `photo_url`. (Pick one name; update Pydantic models; backwards-compatible via Pydantic field aliases if needed.)
- One frontend `<Avatar>` component handles the fallback (`ui-avatars.com` with the user's display name) and accepts `src`, `name`, `size`.

**C. Error messages are pasted everywhere.**
51+ instances of `err?.response?.data?.detail || 'fallback'`. Some use `addToast`, some `setError`, one (`ProfileEditor.jsx:47`) does a `typeof detail === 'string'` check. `BookingDialog.jsx:151-169` has status-code-specific bespoke messages.

**Proposed fix:**
- `frontend/src/utils/errors.js` with `getErrorMessage(err, fallback)` + `getErrorByStatus(err, { 402, 409, fallback })`.
- Single replacement pass to consume it.

**D. Date/time formatting has 8+ distinct call sites.**
`toLocaleString()`, `toLocaleDateString()` with bespoke options, `toLocaleTimeString()`, manual math, `Intl.DateTimeFormat`, raw `toISOString()`.

**Proposed fix:**
- `frontend/src/utils/dates.js` with `formatDateTime`, `formatDateShort`, `formatTimeShort`, `formatRelative` (the "in 2 hours" style used by `NextLessonBanner`).
- One sweep.

**E. Tutor policy fields are fetched from inconsistent endpoints.**
- `cancellation_cutoff_hours` — fetched by `BookingDialog` from `/tutor/policy`, by `CancellationPolicy` from `/tutor/me`.
- `min_booking_lead_minutes` — fetched only by `BookingLeadTimePolicy` from `/tutor/me`.
- `free_trial_minutes` + `offers_free_trial` — owned by `/tutor/trial` (TrialSettings), but read inline off `tutor` objects in `Library`, `TutorHome`, `PricingGrid`.

**Proposed fix:**
- `/tutor/me` is the single source for *everything* a tutor policy panel needs. Other endpoints stay for write paths but reads consolidate.

**F. Components over 400 lines.**
Inbox 544, Navbar 540, CustomThemeCard 538, StaffSupport 519, AdminGrants 465, others. Not blocking but flags refactor candidates.

### Playwright tests that would catch these
- "Booking card renders consistently in MyBookings vs OverviewPanel."
- "Tutor avatar shows on the marketplace, the discovery feed, and the tutor's own site." (Different field names today; tests pass because each view fetches and renders independently.)

## 4. Migration tree

**Status:** single Alembic head (`20260620a_min_booking_lead`). No multi-head problem currently.

**Anomaly:** `backend/migrations/versions/20260606_tutor_theme.py:13` declares `down_revision = "20260620_grading_credits"` — a June 6 file points at a June 20 file as its parent. The chain works (Alembic walks the directed graph; date prefixes are file naming convention only), but the visual confusion is real and was the proximate cause of my "two heads" bug yesterday.

**Proposed fix:** rename `20260606_tutor_theme.py` and `20260606b_password_reset.py` (and their downstream chain through `20260617_custom_themes`) to date prefixes that reflect their *actual* position in the chain (e.g. `20260620b_tutor_theme.py`). Pure file rename + revision-id rename; no SQL changes. Schedule for after launch — not blocking.

**Cross-dialect safety:** `20260617_custom_themes.py:104-121` has Postgres-only `ALTER TABLE` SQL guarded by `if conn.dialect.name == "postgresql"`. ✓
`20260607_rename_teacher_to_creator.py:26` correctly double-quotes the `"user"` reserved word for Postgres. ✓

**Entrypoint:** `backend/entrypoint.sh:78` runs `alembic upgrade head` (singular). Safe given single head. Should we ever intentionally introduce branches in the future, switch to `heads`.

## 5. Playwright readiness

**Today:** zero browser-driven tests anywhere. Backend tests are hermetic (sqlite in-memory, `backend/tests/conftest.py:21`) and pass 447 cases, but no test exercises the React shell.

**Proposal:**
1. Add Playwright as a dev dependency in `frontend/package.json`.
2. Create `frontend/tests/e2e/` with a fixture file that:
   - Boots the Vite dev server (or runs against a deployed URL).
   - Seeds a test admin + test tutor + test student via direct HTTP to the API.
   - Returns helpers (`loginAs(email, password)`, `bookTrial(tutorSlug)`, etc.).
3. Write one spec per E2E_TESTING.md section. The first three I'd write:
   - **Trial booking happy path** (would have caught the `LessonPack.deleted_at` bug.)
   - **Mark complete timing gate** (catches any future regression on the new feature.)
   - **Cross-subdomain SSO** (apex login → click into tutor subdomain → no second login.)
4. Run the suite locally before every deploy. CI can come later.

**Cost estimate:** Playwright install + scaffold + 3 specs is one focused half-day. Each additional spec is ~30 minutes once the fixtures exist.

## Proposed sequencing

The work breaks into five self-contained slices. Each is independently testable + deployable.

**Slice E — Playwright suite scaffold + first three specs.**
- Should land before any of A–D ship to act as the verification harness.
- *Estimated: half-day.*

**Slice A — Mark complete + no-show (Critical #1, #2)**
- Add `NO_SHOW` enum value + migration.
- Add timing gate to `/bookings/{id}/complete`.
- Add `/bookings/{id}/no-show` endpoint.
- Frontend `BookingsManager.jsx` renders the two new affordances with disabled tooltips when ungated.
- Playwright spec for both flows.
- *Estimated: half-day with verification.*

**Slice B — Auth surface finishing (High #4, #5)**
- WS endpoints read the cookie.
- StaffSupport + ModulesStorefront switch to `currentUser`.
- `get_current_user_optional` honours `token_invalidation_at`.
- Add a Playwright spec for SSO + inbox realtime.
- *Estimated: half-day with verification.*

**Slice C — Booking lifecycle hardening (High #3, Medium #8)**
- Recurring generator honours lead + cutoff.
- Cancel/complete/reschedule become idempotent.
- *Estimated: half-day.*

**Slice D — Frontend hygiene (Medium #6, #7, #9)**
- One `<BookingCard>`, one `<Avatar>`, one `errors.js`, one `dates.js`.
- Backend returns consistent `photo_url` everywhere.
- One sweep replacing ~60 call sites.
- Largest slice; *estimated: full day.*

**Recommended order:** E → A → B → C → D. E first because it's the safety net for the rest. A and B are the highest-severity bugs. C is the cleanup. D is the polish.
